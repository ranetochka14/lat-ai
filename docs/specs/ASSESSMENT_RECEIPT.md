# LAT AI — чтение сохранённого результата AI-оценки

AI-часть восстановления реализует приватный `POST /assess/receipt` на том же
локальном worker. Запрос только читает журнал: не вызывает модель, не создаёт
строку, не ожидает завершения активной генерации и не повторяет её.

Это подготовленная возможность для backend-разработчика. Django, frontend,
автоматическая сверка после сбоя и пользовательская история не изменены.

## Запрос и граница доверия

Требуются прежние `Content-Type: application/json` и секрет `X-LAT-IPC`.
Браузерный Origin запрещён, лимит тела и loopback-привязка прежние. Секрет
не передавать в браузер. POST используется для передачи приватного текста в
теле; несмотря на метод, операция не изменяет состояние.

```json
{
  "body": {"request_id":"UUID исходного запроса", "answer":"исходный ответ"},
  "resolved": {
    "actor_id":11,
    "attempt_id":27,
    "digest":"SHA256 доверенного задания",
    "task_key":"L1.types.1"
  }
}
```

Отпечаток запроса вычисляется той же функцией, что и `/assess`: actor/request ID,
ответ, attempt ID, digest, task key и текущий файл рубрик с ревизией.
Все поля должны быть восстановлены backend из доверенного состояния, а не
приняты от браузера без проверки прав. Другой actor получает `not_found`.
Изменённые ответ/попытка/задача/digest/рубрика дают409 `request_conflict`.
Старую ревизию нельзя незаметно принять за текущую.

## Ответ

При успешном чтении HTTP200:

```json
{
  "contract_version":"1.0",
  "request_id":"UUID исходного запроса",
  "state":"completed",
  "assessment_revision":"ревизия текущего AI-оценщика",
  "receipt":{"status":200,"body":{"contract_version":"1.0","request_id":"UUID исходного запроса","outcome":"assessed","checks":[true,true,true],"evidence":["цитата1","цитата2","цитата3"],"rubric_version":"local-assessment-v1"}}
}
```

- `not_found`: записи нет; `receipt` отсутствует. Это не разрешение повторить
  неизвестный POST — мог быть изменён контекст или потеряны исходные параметры.
- `pending_unknown`: запись есть, итоговой квитанции нет. Возвращается сразу,
  в том числе после перезапуска worker. Никакого таймера для повторной генерации.
- `completed`: вложенная `receipt` в точности содержит сохранённые status/body.
  Она может иметь status503/outcome=unavailable: completed означает завершение
  работы, а не наличие оценки. Отсутствующие checks нельзя превращать в ноль.
- Невалидный запрос —400; конфликт параметров —409; ошибка журнала —503.

## Что остаётся backend/frontend

Backend должен сохранять параметры до отправки запроса, проверять actor/права,
сравнивать текущую задачу и атомарно применять только подходящую квитанцию.
Ручная проверка имеет приоритет. Повтор чтения не создаёт новый прогресс или
попытку. Frontend отдельно согласует понятное отображение неизвестного исхода.

AI-тесты проверяют отсутствие генерации/записей при чтении, pending во время
работы и после открытия журнала, точное чтение successful/unavailable квитанций,
изоляцию actor, конфликты всех частей отпечатка запроса и прежнюю IPC-защиту.
Это не сквозная проверка аварии Django: она остаётся задачей команды.
