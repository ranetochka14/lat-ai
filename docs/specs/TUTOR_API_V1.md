# LAT AI — контракт ИИ-репетитора v1.0

10.11.2026. **Кандидат контракта для команды**, адаптер I02.1 и локальная интеграция I02.2. Django endpoint подключён для ручной проверки; приёмка командой и промышленное развёртывание не заявляются. Базовый каркас main@b4fd6370d31dab24c924d7d78cc4dfffa478e30c; ядро LAT AI v10 неизменно. Бренд сайта LAT AI сохранён.

## Граница ответственности

Браузер → `POST /api/v1/tutor/ask/` Django → проверка JWT, доступа и связей ресурсов → сопоставление опубликованного учебного содержания с L1/L2 → существующий ИИ-модуль. Django остаётся владельцем пользователей и прогресса. Модуль не принимает пользовательскую роль, токен, счётчики или разрешение решения из тела запроса. ИИ не назначает оценки и не переводит упражнения в checked.

Этот этап поставляет схему, примеры и функции Node `prepareRequest`, `toPublicResponse`, `errorResponse`. Это библиотечная граница, не HTTP-сервис и не замена Django. В I02.2 добавлены приватный loopback worker, Django view/serializer, постоянный replay и UI; инструкция в I02_2_RUN.md. Нельзя просто выставить библиотеку в сеть: она принимает уже доверенный контекст как аргумент, а не проверяет JWT сама.

## Публичный запрос

Заголовки: `Authorization: Bearer <access token>`, `Content-Type: application/json`, ответ JSON. Токен никогда не попадает в model prompt. JSON после декодирования HTTP transfer — максимум **49152 байта**; превышение413 без обрезки. Это вмещает6000 UTF-16 единиц даже с JSON-экранированием. CORS остаётся ограничен разрешённым адресом сайта. Только существующая авторизованная сессия.

```json
{
  "contract_version": "1.0",
  "request_id": "d7ae9b27-2c00-4b18-a300-e526bda91501",
  "action": "explain",
  "question": "Почему выполняется эта ветка?",
  "course_id": 11,
  "lesson_id": 21,
  "exercise_id": 31,
  "mode": "internal",
  "document_ids": [],
  "code_context": {
    "code": "age = 14\nif age >= 12:\n    print(\"Можно\")",
    "revision": 7,
    "selection": {"start": 9, "end": 22}
  }
}
```

IDs11/21/31 — **синтетический пример**, не реальные соответствия в БД. Схема: `contracts/tutor-v1.request.schema.json`.

| Поле | Правило |
|---|---|
| contract_version | Обязательно, строка `1.0`. |
| request_id | Обязательно, UUIDv4 в нижнем регистре из crypto.randomUUID(); новый ID для нового действия, прежний для сетевого повтора. |
| action | Обязательно, `explain` или `hint`. Это техническое действие, не account.role. Ученик не обязан выбирать его: обычная отправка explain, кнопка подсказки hint. |
| question | Обязательно, непустой видимый текст;1..2000 UTF-16 единиц, корректный Unicode. Cc управляющие символы запрещены, кроме LF/CR/TAB; вопрос из одних пробельных/невидимых символов запрещён. Не trim/нормализовать перед моделью. |
| course_id, lesson_id | Обязательно, положительные safe integers≤9007199254740991. UI берёт из текущего урока; сервер проверяет существование, публикацию, доступ и связь урока с курсом. |
| exercise_id | Необязательно: положительный safe integer или null. Для обычной подсказки hint требуется ID точного упражнения — это семантическая проверка после policy, отсутствие даёт422. Кризисная hint-реплика может получить200policy без exercise_id. Сервер проверяет связь переданного упражнения с уроком; похожего заголовка недостаточно для назначения task_key. |
| mode | Необязательно, только `internal`, значение по умолчанию. `personal` пока422: RAG не подключён. |
| document_ids | Необязательно, только пустой список. Непустой список422; нельзя молча игнорировать материалы. |
| code_context | Необязательно. При отсутствии кода **не передавать**; null запрещён. Объект снимка ниже. |

Неизвестные поля запрещены на всех уровнях. В частности, запрещены `user_id`, `role`, `lesson`, `topic`, `task_id`, `level`, `attempts_count`, `hints_used`, `events`, `allowSolution`, `system_prompt`. DRF по умолчанию может игнорировать лишние поля: будущий serializer должен явно запрещать их. Старое тело без contract_version получает400, а не угадывание версии. Это явное изменение заглушки; действующего UI вызова tutor в базовом каркасе нет.

## Код, выделение и устаревшие ответы

`code_context` имеет ровно `code`, `revision`, `selection`. code≤4000 UTF-16 единиц; revision — неотрицательное safe integer; selection — null или `{start,end}`. start включительно,end исключительно,0≤start<end≤code.length. Нельзя разрывать surrogate pair или пару CRLF. Пустое выделение браузер передаёт как null; некорректный диапазон сервер отклоняет400. Вопрос+код≤6000 единиц. Ничего не обрезается молча.

Один emoji занимает2 единицы; Python `len()` считает иначе. Для длины вPython использовать `len(text.encode('utf-16-le'))//2` после строгой проверки Unicode; границы смещений проверяются по той же UTF-16 записи. JSON Schema maxLength считает Unicode code points: дополнительные UTF-16 проверки **обязательны**, одних схем недостаточно. CRLF не преобразовывать вLF между получением снимка и проверкой выделения.

Браузер до отправки фиксирует question,полный code,revision,selection и request_id вместе. Фокус может переходить в чат, выделение не теряется. При правке кода revision растёт, выделение сбрасывается. Возврат текста назад не возвращает revision. Результат привязан к снимку request_id/revision; при несовпадении с текущим редактором показать «Ответ к предыдущей версии кода». Сравнивать также request_id, чтобы поздний ответ не заменял новый. Снимок старого вопроса сохраняется локально в UI до явной очистки, не вычитывается из текущего редактора при получении ответа.

Модель видит весь снимок; focus отмечает предмет вопроса. Проверяется **весь** код, включая невыделенные комментарии. Это недоверенный исходный текст, `execution:not_run`; нельзя утверждать, что код исполнялся, или считать это попыткой. При отсутствии кода контекст отсутствует, не создаётся фиктивный пустой снимок. Допустим явный снимок пустого редактора с selection:null.

## Доверенный аргумент адаптера (НЕ тело браузерного запроса)

Сигнатура: `prepareRequest(body, resolvedContext)`.

```json
{
  "actor_id": 5,
  "access": "granted",
  "course_id": 11,
  "lesson_id": 21,
  "exercise_id": 31,
  "mapping_version": "team-map-v1",
  "lesson_key": "L1",
  "topic": "условия",
  "task_key": "practice.age",
  "hint_events": []
}
```

Этот пример также синтетический. Django сначала проверяет JWT, затем доступ/связи IDs и соответствие опубликованного содержания. Соответствия для основной БД заполняет команда backend. Локальный профиль содержит отдельные 2 урока и 4 точных упражнения: mapping создаётся по фактическим ID и связан с хешем содержания. Случайные ID чужой БД не сопоставляются автоматически. `lesson_key` толькоL1/L2, без автоматического L1 для математики/неизвестного урока. Доступ может быть granted при отсутствии поддерживаемого mapping — обычный вопрос тогда422. После структурной проверки и доступа приоритетные policy-сигналы отвечают независимо от наличия учебного mapping; кризис не должен превращаться в «урок не поддерживается».

Для hint обязательны проверенное task_key и `hint_events`, связанные с этим actor+exercise. Поддерживаются только точные задания из ядра v10; похожий текст/совпавшая тема не даёт права использовать их готовые примеры. Нет истории —503 `HINT_HISTORY_UNAVAILABLE`, а не выдуманный пустой прогресс. Пустой список допустим только как подтверждённое отсутствие событий. pending/client_claim не становятся verified. checked вDjango не равно passed или освоению: в локальном профиле учитываются только checked с конечной оценкой в пределах max_score. passed означает полный балл, а не освоение; уровень использует число проверенных попыток. Для основной БД критерии подтверждает команда backend. Идентичность попыток/событий стабильна, повтор не новая попытка.

В каталожной лестнице v1 **четвёртая ступень полного разбора всегда запрещена**: адаптер передаёт allowSolution:false независимо от account.role. Уровень1..3 вычисляет ядро из доверенных событий; у practice.age только1/2. hint_state и разрешения от клиента не принимаются. История/прогресс не возвращаются в ответе. Для свободного explain этот флаг не является смысловой защитой: действуют промпт и выходные проверки ядра, но возможна выдача решения. Explain остаётся unverified и не получает ученический допуск только из-за наличия адаптера.

Приватный `hint_events` — массив не более1000 событий из доверенного хранилища этого actor/упражнения, не из браузера. Поля: `id` и `task_id` — непустые строки≤100; `kind` — attempt или hint; `status` — verified,pending,client_claim. Для attempt требуется boolean `passed`, для hint — integer `level`1..4 (4 допустим в старой истории, но v1 его не выдаёт). Пример: `{"id":"attempt-42","task_id":"practice.age","kind":"attempt","status":"verified","passed":false}`. Пример выданной подсказки: `{"id":"hint-43","task_id":"practice.age","kind":"hint","status":"verified","level":1}`. Ядро считает только verified точного task_id; дубликаты одногоid должны совпадать, пропущенные предшествующие ступени недопустимы. Подтверждённая неуспешная попытка тоже считается попыткой, но не освоением. Backend обязан ограничить чтение своим пользователем/упражнением ещё до этих проверок; фильтрация внутри ядра не является авторизацией.

## Ответ HTTP200

См. исполняемые примеры в contracts/examples. Стабильные поля: contract_version,request_id,outcome,reason,answer,context.

| Поле | Значение |
|---|---|
| outcome | `answer` для model/catalogue; `fallback` для резерва; `policy` для кризиса/приватности/ограничений. |
| reason | Контролируемый код из схемы. Важные: ok,disabled,cold,timeout,transport,quarantined,queue_full,queue_budget,invalid_output,crisis,privacy,solution_request. Не сырое исключение. |
| answer.text | Текст для пользователя. Рендерить текстом, не через innerHTML. Не повторять запрос, код, токен или сырые выходы модели при ошибке. |
| answer.source | `model`, `catalogue`, `template`, `policy`. Шаблон нельзя подписывать модельным объяснением. |
| answer.hint_level | null или1..3; не клиентская настройка. |
| answer.explanation_verification | `unverified` для model; `not_applicable` для остальных. Не утверждать педагогическую приёмку каталога. |
| answer.facts | Отдельный массив `{id,text}` из separated-режима, иначе[]. Не смешивать с неподтверждённым объяснением. |
| answer.facts_review | `not_reviewed_by_teacher` при фактах, иначе `not_applicable`. Технический реестр не означает T01. |
| context | Внешние course_id,lesson_id,exercise_id и code_context:null либо revision,selection с вычисленными start_line/end_line,code_units,execution:not_run. Полный code не эхо-возвращается. |

template после modeloff/таймаута/карантина —200 `fallback`, если имеется корректный резерв. Это не успешная генерация и не счётчик качества model. Отказ/кризис —200 `policy`, не HTTP403. Каталожная подсказка —200 `answer`, source:catalogue, а не «ИИ сгенерировал».

## Ошибки и повтор запроса

Ошибки: `{contract_version:"1.0",request_id:<валидный ID или null>,error:{code,message,retryable:false}}`.

| HTTP | Код / смысл |
|---|---|
|400|INVALID_REQUEST / CONTRACT_VERSION_REQUIRED / INVALID_CODE_CONTEXT — тип, лимит, неизвестное поле, диапазон.|
|401|AUTH_REQUIRED — JWT отсутствует/истёк; обрабатывает Django до адаптера.|
|404|CONTEXT_NOT_AVAILABLE — ресурс отсутствует, недоступен или не связан; одинаковый ответ для защиты от перебора чужих IDs.|
|409|REQUEST_ID_CONFLICT — тот же actor+request_id с другим валидированным содержимым.|
|413|PAYLOAD_TOO_LARGE — предел JSON49152 байт в HTTP-слое.|
|422|UNSUPPORTED_MODE / UNSUPPORTED_CONTEXT / UNSUPPORTED_TASK — персональные материалы, неподдержанный lesson/task mapping.|
|429|RATE_LIMITED — лимит пользователя перед работой модели; Retry-After задаёт сервер.|
|502|INVALID_CORE_RESPONSE — ядро нарушило ожидаемую форму; сырые данные наружу не выводить.|
|503|HINT_HISTORY_UNAVAILABLE / AI_UNAVAILABLE — не удалось получить доверенную историю/связаться с модулем и нет корректного резерва.|

Сам adapter.mjs проверяет данные и проекцию. В I02.2 HTTP-лимит и авторизация реализованы в Django, replay — в общем приватном worker. Код 429 зарезервирован контрактом; отдельная пользовательская квота в локальном профиле не реализована, очередь модели ограничена ядром.

I02.2: ключ идемпотентности `(actor_id,request_id)`; fingerprint канонического валидированного тела с явными defaults и отсортированными ключами. Повтор сверяет доступ заново, затем возвращает тот же сохранённый ответ и не вызывает модель/не выдаёт новую подсказку. Concurrent duplicates выполняются один раз. Идентичные ID разных пользователей изолированы. Новый изменённый вопрос/снимок — новыйID, повторстарогоID с изменением —409. Сохранять fingerprint+ответ+issued-hint атомарно; сбой записи — не отправлять успешный ответ. Не считать transport timeout доказательством завершения запроса. Только outcome:answer,source:catalogue с уровнем подсказки может дать событие hint; policy/fallback/error не продвигают лестницу. Истёкшие ключи не должны внезапно стать новым действием: для демо хранить в течение всей сессии; до продукта определить retention и явный отказ старымID.

Даже при **разных** request_id подсказки одного `(actor_id,exercise_id)` сериализуются: блокировка охватывает загрузку актуальной истории → prepareRequest → Tutor → проверку/проекцию ответа → атомарное сохранение ответа и события → освобождение. В I02.2 собственная история выдачи hints читается после получения блокировки; второй distinct-запрос видит обновлённые hints. Проверенные попытки — доверенный снимок Django, полученный непосредственно перед IPC; параллельную правку преподавателя после этого момента не обещаем учитывать. Все процессы Django обращаются к одному worker. SQLite locking_mode=EXCLUSIVE не допускает второго владельца журнала, synchronous=FULL сохраняет завершённые записи. Это локальная однопроцессная интеграция, не распределённая очередь. История других упражнений/учеников не объединяется.

`fingerprintRequest(body)` фиксирует алгоритм: сначала нормализованное валидное тело (mode=internal,document_ids=[],exercise_id=null при отсутствии; code_context остаётся отсутствующим), затем рекурсивная сортировка ключей, компактный JSON без ASCII-экранирования Unicode, SHA256 от UTF-8. Включены request_id и revision, порядок полей не влияет, пробелы внутри question/code не удаляются. В Python JSON-целые нормализуются к int (не bool), ensure_ascii=False,separators=(',',':'),sort_keys=True. Контрольные векторы в contracts/examples/fingerprint-vectors.json. Digest приватный; авторизация и ключ actor_id остаются отдельными. Функция сама ничего не хранит; в I02.2 её использует bridge.mjs для постоянного replay. Unicode-экранирование IPC не меняет отпечаток после JSON-декодирования.

## Время, журналы и границы показа

Один общий Tutor/координатор на экземпляр модели, не новый на каждый запрос. Ядро имеет8с на очередь/генерацию/валидацию; целевой полный ответ10с включаетDjango,доступ/историю,IPC,проекцию. Старт модели — отдельная операция оператора, не первый вопрос ученика. Не запускать новыйPOST по автоматическому повтору после таймаута. Карантин/восстановление R01 сохраняются; HTTPобрыв не доказывает остановку модели. Короткий живой HTTP smoke в I02.2 измерен; полная проверка холодного старта и длительной нагрузки L01 остаётся отдельной задачей.

Runtime-журнал: request_id,action,outcome,source,reason,version,mapping_version,длительности этапов,число единиц кода/границы выделения. Не сохранять JWT,question,code,model prompt,сырые ответы,профиль/контакты. Сохранение ответа для replay — отдельное защищённое хранилище с ограниченным сроком, не обычный runtime-log. Метаданные безопасности берутся из утверждённого набора, а не текста пользователя.

Никакого изменения user.role,отключенияJWT/CORS,новыхвесов,платногоAPI,RAG или автоматической проверки произвольного ученического кода. Запуск Python/редактор — отдельный существующий интерфейсный сценарий; передача code_context не добавляет выполнение. Модель и полный разбор остаютсяoff по умолчанию, человеческие T01/S02 и E01/F01/L01 не закрываются этим контрактом. Статический server.cjs отдаёт только index.html и assets/ до и после realpath; integration и .runtime приватны, включая короткие имена NTFS. Frontend подключает редактор через assets/tutor.js. Запуск START_AI_REVIEW.cmd явно включает модель для взрослого оператора; по умолчанию сам worker стартует с моделью off.

## I02.2 — детали локального восстановления

HTTP retry сохраняет request_id и снимок. Незавершённая запись после аварии возвращает 503 с retryable:false и не регенерируется. Клиент предлагает повтор только при сетевой ошибке, а новый вопрос создаёт новый ID. История hint и сохранённый ответ фиксируются одной транзакцией. Изменение mapping при повторе даёт 409: старый ответ не выдаётся под новым учебным содержанием. Рабочий журнал и Django БД резервируются вместе; нельзя сбрасывать только одну из них и переиспользовать actor IDs.
